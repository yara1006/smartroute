# SmartRoute AI 复盘文档

> 记录关键架构决策、trade-off 分析、踩过的坑，以及如果重做一次会怎么改。

---

## 1. 服务层拆分：为什么拆 6 个模块而不是放 api.py？

**背景**：初始版本 `api.py` 有 2868 行，所有业务逻辑堆在一个文件里。

**决策**：拆分为 `services/` 下 6 个独立模块，通过 `route_service.py` 作为 re-export facade 保持向后兼容。

**Trade-off**：
- ✅ 单测可独立跑，`test_adjustment.py` 只测调整逻辑，不需要启动 FastAPI
- ✅ 职责清晰，`anchor_service.py` 只管地点解析，`route_builder.py` 只管路线构建
- ✅ 新加功能时只需改对应模块，不用在 2800 行文件里找位置
- ❌ 跨模块依赖需要显式导入（踩坑：`route_builder.py` 调 `city_hint_from` 但没导入，测试报 NameError）
- ❌ `route_service.py` 是纯转发层，增加了理解成本

**如果重做**：会用 Python 包（`services/__init__.py`）代替 re-export facade，更 Pythonic。

## 2. TSP 路线排序：为什么用贪心而不是 DP/精确解？

**背景**：路线规划本质是旅行商问题（TSP），需要找到最短路径访问所有站点。

**决策**：用 O(n²) 贪心最近邻算法替代 O(n!) 全排列。

**Trade-off**：
- ✅ 10 个站点时，贪心 <1ms，全排列需要数秒
- ✅ 实测质量损失 <5%（站点数 ≤10 时，贪心解接近最优）
- ❌ 极端情况下可能不是全局最优（例如站点呈环形分布）
- ❌ 没有理论最优性保证

**如果重做**：会加一个 `optimization_level` 参数，≤6 站点用精确解，>6 用贪心。

## 3. LLM 优先 + 规则兜底：为什么不全用 LLM？

**背景**：意图解析可以用 DeepSeek LLM，也可以用关键词规则。

**决策**：LLM 优先（有 Key 时），规则兜底（无 Key 或超时）。

**Trade-off**：
- ✅ 无 Key 时 demo 仍能跑通，评委不会看到"服务不可用"
- ✅ LLM 能处理复杂意图（"少走路、便宜点、加个咖啡"），规则只能处理简单模式
- ❌ 规则兜底的准确率低于 LLM（实测约 70% vs 90%+）
-  需要维护两套解析逻辑，增加代码量

**如果重做**：会把规则兜底做成 LLM 的 fallback chain，而不是平行实现。

## 4. 安全边界：为什么拦截预订而不是放行？

**背景**：用户可能说"帮我预订这家餐厅"。

**决策**：`safety_reviewer.py` 拦截所有高风险动作（预订/付款/凭据/法律确认），返回 `refused=true` + 警告信息。

**Trade-off**：
- ✅ 合规：个人项目无支付资质，不能处理真实交易
- ✅ 安全：防止误操作（用户说"帮我订不可退款的酒店"，系统提示风险）
- ❌ 功能受限：不能做成完整的"一站式"体验
- ❌ 用户可能觉得"不够智能"

**如果重做**：会加一个 `handoff_url` 字段，拦截时返回官方平台链接（如美团/大众点评），而不是只说"不行"。

## 5. 缓存策略：为什么用 30 分钟 TTL 而不是更长？

**背景**：高德 Web 服务有 QPS 限制和配额，需要缓存减少调用。

**决策**：30 分钟 TTL + 500 条目上限。

**Trade-off**：
- ✅ 演示场景下，同一地点 30 分钟内数据基本不变
- ✅ 500 条目上限防止内存泄漏（之前无上限，长时间运行 OOM）
- ❌ 实时性差：营业状态变化、临时闭馆无法及时反映
-  30 分钟是拍脑袋的，没有数据支撑

**如果重做**：会根据 API 配额动态调整 TTL（配额紧张时延长到 1 小时，宽松时缩短到 10 分钟）。

## 6. 前端架构：为什么从单文件拆成组件？

**背景**：初始版本 `App.jsx` 有 2691 行，所有 UI 逻辑堆在一起。

**决策**：拆分为 `Panels.jsx`、`PhoneExperience.jsx`、`RouteMap.jsx`、`QueryComposer.jsx`、`ErrorBoundary.jsx`。

**Trade-off**：
- ✅ 组件可独立测试（`ErrorBoundary.test.jsx`）
- ✅ 职责清晰，`RouteMap.jsx` 只管地图渲染
- ❌ 组件间状态管理变复杂（需要 prop drilling 或 context）
- ❌ 拆分边界不好把握（`Panels.jsx` 还是偏大）

**如果重做**：会用 Zustand 或 Jotai 做状态管理，而不是 prop drilling。

## 7. 测试策略：为什么覆盖率定 80% 而不是 100%？

**背景**：可以追求 100% 覆盖率，也可以接受更低的阈值。

**决策**：`fail_under=80`，实际达到 82-83%。

**Trade-off**：
- ✅ 80% 覆盖核心业务逻辑，边际收益递减的部分（getter/setter、常量定义）不强制
- ✅ 测试运行快（200 个用例 <10 秒），CI 不拖慢
- ❌ 有 17-18% 的代码没测到（主要是异常分支、边缘情况）
-  覆盖率数字可能误导（80% 覆盖的不一定是关键路径）

**如果重做**：会加关键路径标记（`# critical`），确保核心链路 100% 覆盖，其他部分 80%。

## 8. 如果重做一次，会改什么？

### 架构层面
1. **加向量数据库**：用 Qdrant/Chroma 替代本地 JSON 索引，支持语义检索
2. **异步任务队列**：用 Celery/RQ 处理耗时规划，API 立即返回任务 ID
3. **模型路由**：L1 层抽象更彻底，支持 OpenAI/Anthropic/本地模型热切换

### 工程层面
4. **GraphQL API**：替代 REST，前端按需查询路线字段
5. **WebSocket 实时推送**：规划过程中推送进度，而不是等完成后一次性返回
6. **OpenTelemetry 追踪**：替代自建 `tool_trace`，接入 Jaeger/Zipkin

### 产品层面
7. **多轮对话**：支持"刚才那条路线太贵了，换一条"的上下文理解
8. **协同规划**：多人各自提交偏好，系统生成妥协方案
9. **离线模式**：PWA + Service Worker，无网络时仍可查看已保存路线

## 9. 踩过的坑

| 坑 | 原因 | 解决 |
|---|------|------|
| `route_builder.py` 报 `NameError: city_hint_from` | 跨模块依赖没显式导入 | 加 `from services.anchor_service import ...` |
| 高德 `USERKEY_PLAT_NOMATCH` | 误填 JS API Key 到 Web 服务 Key | 启动时校验 Key 类型，日志提示 |
| 缓存 OOM | 无上限，长时间运行积累 | 加 `AMAP_CACHE_MAX_ENTRIES=500` + 定期清理 |
| 前端测试 0 覆盖 | 没配 Vitest | 加 `vite.config.js` + `@testing-library/react` |
| 架构图例重叠 | SVG 高度不够，图例和基础设施行重叠 | 加大 viewBox，图例下移 30px |
| GitHub 图片缓存 | SVG 更新后 README 仍显示旧版 | URL 加 `?v=2` 查询参数绕过缓存 |
